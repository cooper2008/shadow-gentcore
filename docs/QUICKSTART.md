# Quickstart — 5 minutes from zero to running agent

Skip the guided tour. This is the fastest path from a fresh machine to an agent writing real code.

---

## 0. Prerequisites

- Python 3.11+
- Git
- One LLM credential (any of: Anthropic, OpenAI, Gemini, GLM, Minimax, or an AWS Bedrock profile)

---

## 1. Clone the template and bootstrap the framework

The fastest path uses the template's one-command bootstrap:

```bash
cd ~
git clone <org>/gentcore-template my-backend
cd my-backend
make bootstrap           # clones agent-contracts + agent-tools + shadow-gentcore, sets up venv, smoke-checks
```

What `make bootstrap` does for you:

- Clones `agent-contracts`, `agent-tools`, `shadow-gentcore` side-by-side into `../framework/` (override with `GENTCORE_FRAMEWORK_DIR`)
- Creates a Python 3.11 venv inside `shadow-gentcore/.venv`
- Installs all four packages in editable mode
- Runs `./ai workspace` + preflight smoke checks to confirm everything links up

### Manual path (if you prefer)

```bash
cd ~
git clone <org>/agent-contracts
git clone <org>/agent-tools
git clone <org>/shadow-gentcore
git clone <org>/gentcore-template my-backend
cd shadow-gentcore
python3.11 -m venv .venv
.venv/bin/pip install -e ../agent-contracts -e ../agent-tools -e ".[dev]"
```

## 2. Sanity check

```bash
cd ~/shadow-gentcore
.venv/bin/pytest harness/tests/ -q     # ~2090+ passed
```

---

## 3. Register your domain

Edit `shadow-gentcore/config/workspace.yaml`:

```yaml
teams:
  my-backend:
    industry: ecommerce
    trusted: true
    reference:
      - path: ../my-backend/src              # Genesis reads this as "how we do things"
    target:
      - path: ../my-backend/src              # What agents are allowed to modify
      - path: ../my-backend/tests
    docs:
      - path: ../my-backend/docs             # Optional domain docs
```

Edit `my-backend/domain.yaml` and set the `name:` + `purpose:` fields.

---

## 4. Smoke test (zero cost, no API key needed)

```bash
./ai test smoke                              # full simulated journey
./ai test smoke --domain ../my-backend       # health-check your domain once it's built
```

Expected: `13/13 steps passed`. If this fails, something is wrong with the install — don't proceed until it's green.

## 6. Run genesis — build your domain's agents

```bash
# Path-based (no workspace.yaml registration needed) — recommended:
./ai genesis build --domain /path/to/my-backend

# Or, if you've registered the team in shadow-gentcore/config/workspace.yaml:
./ai genesis build --team my-backend
```

What happens (11 steps, takes 5-30 minutes against a real LLM, costs ~$0.30-3 depending on model):

1. **scan** — `SourceScannerAgent` walks `reference/` + `target/` + `docs/`, builds an evidence-tagged file inventory
2. **map** — `KnowledgeMapperAgent` classifies findings, scores `coverage` per category
3. **resolve** — `ConflictResolverAgent` arbitrates when reference repos disagree (6-rung tiebreaker ladder)
4. **discover_tools** — `ToolDiscoveryAgent` picks tool packs matching your stack (`toolpack://core/fastapi`, etc.)
5. **engineer_context** — `ContextEngineerAgent` writes `context/standards.md` + `context/architecture.md`
6. **verify** — `ContextVerifierAgent` re-reads cited sources, scores `grounding_score`
7. **advise** — `BestPracticeAdvisorAgent` writes `context/best_practices.md` (Tier 1.5 overlay) flagging missing-but-recommended industry standards
8. **synthesize_tools** — `ToolSynthesizerAgent` closes tool gaps with MCP servers / synthesized packs (gated by static security scan)
9. **architect** — `AgentArchitectAgent/v2` designs the agent roster + workflow DAG with gates and feedback loops
10. **build** — `AgentBuilderAgent` emits every agent manifest, prompt, grading_criteria, workflow YAML
11. **validate** — `QualityGateAgent` runs structural checks on the output

> **Strict mode for production:** set `GENTCORE_STRICT_MANIFESTS=1` to fail fast on any manifest schema drift instead of warning. Recommended for CI and HTTP server startup.

### What genesis just wrote for you

**Every file below was machine-generated.** You do not author these — re-run genesis if you want different gates, loops, or agents.

```
my-backend/
├── domain.yaml                 # YOU wrote this (1 required file)
├── context/                    # ← generated by ContextEngineerAgent
│   ├── standards.md            #   coding conventions, injected into every agent
│   └── architecture.md         #   system overview, injected on demand
├── agents/                     # ← generated by AgentBuilderAgent (catalog-reused or synthesised)
│   ├── APIFeaturePlannerAgent/v1/   → reasoning mode
│   ├── FastAPICodeGenAgent/v1/      → react mode, file_write + shell_exec
│   ├── PytestRunnerAgent/v1/        → react mode, runs py_compile + pytest
│   ├── CodeReviewerAgent/v1/        → reasoning mode, reads + grades
│   └── TriageAgent/v1/              → self_ask mode, classifies incoming tasks
└── workflows/                  # ← generated by AgentBuilderAgent (one per task type)
    ├── triage.yaml             #   ★ single /run entry — dispatches to the right workflow
    ├── feature_delivery.yaml   #   plan → implement → test → review
    ├── bug_fix.yaml            #   reproduce → fix → verify → review
    ├── refactor.yaml           #   plan → apply → test → review
    └── docs_refresh.yaml       #   audit → regenerate → review
```

**Override auto-discovery in `domain.yaml`** (optional — genesis auto-discovers by default from git log, issue templates, CONTRIBUTING.md):

```yaml
# my-backend/domain.yaml
workflows:
  # Option A — full override
  processes: [feature_delivery, bug_fix, security_review]

  # Option B — deltas over auto-discovery (keep what genesis finds, add/remove)
  add_processes:    [gdpr_erase]
  exclude_processes: [refactor]

  # Optional — explicit triage dispatcher
  triage:
    classifier: "_shared/TriageAgent/v1"
    buckets:  [feature, bug, security]
    routes:   {feature: feature_delivery, bug: bug_fix, security: security_review, unknown: human_review}
```

**Here's what the generated `feature_delivery.yaml` contains** — self-healing DAG with gates, feedback loops, and reset points, all emitted by AgentArchitectAgent + AgentBuilderAgent:

```yaml
# my-backend/workflows/feature_delivery.yaml  ← 100% machine-generated
name: feature_delivery
version: "2.0.0"

steps:
  - name: plan
    agent: my-backend/APIFeaturePlannerAgent/v1
    gate: {condition: "status == success", on_fail: retry, max_retries: 1}

  - name: implement
    agent: my-backend/FastAPICodeGenAgent/v1
    depends_on: [plan]
    gate: {condition: "status == success", on_fail: retry, max_retries: 2}

  - name: test
    agent: my-backend/PytestRunnerAgent/v1
    depends_on: [implement]
    gate:
      condition: "all_passed == true"        # semantic gate — not just "step returned"
      on_fail: retry
      max_retries: 2
      fallback_step: implement

  - name: review
    agent: my-backend/CodeReviewerAgent/v1
    depends_on: [test]
    gate:
      condition: "approved == true"
      on_fail: retry
      fallback_step: implement

reset_points: [implement]                    # checkpoint for rollback

feedback_loops:                              # self-healing paths
  - from_step: test
    to_step: implement
    condition: "all_passed == false"
    max_iterations: 2
  - from_step: review
    to_step: implement
    condition: "approved == false"
    max_iterations: 2
```

Verify the generated domain is healthy:

```bash
./ai test smoke --domain ../my-backend
# Score: 100%     N agents, N workflows
```

> **You do not write the workflow YAML above.** It's machine-generated from the architect's design. To change gate conditions, feedback loops, or the agent roster, re-run `./ai genesis build --team my-backend` with a refined `domain.yaml` (e.g. tighter `workspace_policy`, different `capabilities`, or richer `context/` docs).

## 7. Run your generated workflow on a real task

The multi-agent fleet and the self-healing workflow are **already there** — you just hand them a task.

**Single agent (narrow surface):**

```bash
./ai run agent my-backend/FastAPICodeGenAgent/v1 \
  --task "Add a GET /items/{item_id}/reviews endpoint with cursor pagination" \
  --domain ../my-backend
```

**Full self-healing workflow (everything genesis wrote, coordinated end-to-end):**

```bash
./ai run workflow ../my-backend/workflows/feature_delivery.yaml \
  --domain ../my-backend \
  --task '{
    "feature_request": "Add product search by name and price range",
    "branch": "feat/product-search",
    "workspace_root": "/path/to/your/working/tree",
    "acceptance_criteria": ["?q=<name>&min=<num>&max=<num>", "paginated results", "tests cover edge cases"]
  }'
```

> **`workspace_root` is required for files to land on disk.** Code-writing
> agents (CodeWriter, MigrationAgent, TestRunner, RefactorPlanner) emit
> `files: [{path, content}]` arrays in their structured output. The
> framework writes those files under `workspace_root` only when the
> agent's manifest declares `persist_files: true` (Builder defaults this
> to true for code-writing agents). Without `workspace_root` the agent
> still runs but its output dies in Tier 4 memory rather than reaching
> your filesystem.

What you'll see:

- `plan` step produces a file-level plan
- `implement` step calls `file_write` to create models, schemas, services, routers, migrations, tests
- `test` step runs `python -m py_compile` + `pytest` on what was written
- `review` step approves or requests changes
- If `test` fails or `review` rejects → feedback loop routes back to `implement` with failure context, up to `max_iterations: 2`

---

## 8. Watch the self-healing loop

The `execution_log` in the workflow result shows every gate decision:

```
[step_started             ] plan
[gate_passed              ] plan
[step_started             ] implement
[gate_passed              ] implement
[step_started             ] test
[output_validation_failed ] test       → all_passed=false, errors=[...]
[feedback_loop_triggered  ] test → implement (iteration 1)
[gate_retry               ] attempt 1, strategy: retry_with_feedback
[gate_passed_on_retry     ] test       → all_passed=true
[step_started             ] review
[gate_passed              ] review     → approved=true
overall status: completed
```

That's the framework catching a bug, jumping back to `implement` with the test failure as context, and converging.

# Automation Guide — running domain agents against real work

Once genesis has built your domain, you have a fleet of agents. This guide is the practical playbook for **making them do real work automatically** — on tasks from your backlog, via GitHub Actions, on a schedule, or in response to webhooks.

If you haven't run genesis yet, start with [QUICKSTART.md](QUICKSTART.md) or [USER_GUIDE_END_TO_END.md](USER_GUIDE_END_TO_END.md).

---

## The three levels of automation

| Level | What triggers | Who approves | Typical use |
|-------|---------------|--------------|-------------|
| **Manual** | You run `./ai run workflow ...` | You review the diff | Feature work on a branch |
| **Semi-auto** | GitHub Action / Linear webhook | PR review before merge | Bug fixes, small features, dep upgrades |
| **Fully auto** | Cron / webhook, auto-merge on green | Only if gates all pass | Docs refresh, typo fixes, pin bumps |

Start manual. Move to semi-auto when you trust the gates. Only go fully auto for narrowly-scoped reversible tasks.

---

> ### 📌 About the workflow YAMLs in the examples below
>
> Every `workflows/*.yaml` you see referenced in this guide is **generated by `AgentBuilderAgent` during `./ai genesis build`.** You do not author it.
>
> The architect picks gate conditions, feedback loops, and reset points based on your domain's capabilities and context; the builder transposes that design into YAML. If you want to change the shape of the workflow (different gates, extra feedback loops, new agents), **refine `domain.yaml` and re-run genesis** — don't hand-edit the generated files.
>
> Some scripts in `shadow-gentcore/scripts/*.py` use a **hand-scaffolded** workflow variant for proof-of-concept smoke runs (where we wanted a known-good fixture for provider testing). Production usage is always genesis-emitted.

## Level 1 — manual runs (start here)

### Single agent

Simplest surface. Good when you want to exercise one piece of the domain:

```bash
./ai run agent my-backend/FastAPICodeGenAgent/v1 \
  --task "Add a cursor-paginated GET /users/{id}/sessions endpoint" \
  --domain ../my-backend
```

Output: the agent writes files in place, emits structured JSON, prints a summary.

### Full workflow

```bash
./ai run workflow ../my-backend/workflows/feature_delivery.yaml \
  --task '{
    "feature": "Add product search by name and price range",
    "acceptance_criteria": [
      "Query: ?q=<name>&min=<num>&max=<num>",
      "Paginated via ?cursor= and ?limit=",
      "Returns 200 with items[], next_cursor",
      "Tests cover happy + invalid-query + empty"
    ]
  }'
```

The workflow runs plan → implement → test → review with gates, feedback loops, and retries. Watch the `execution_log` in the output for every gate decision.

### Always smoke first

Before running against real money:

```bash
./ai test smoke --domain ../my-backend       # 100% score required
./ai run workflow PATH --task '...' --dry-run  # proves the DAG executes
```

## Level 2 — semi-automated via GitHub Actions

Recommended pattern for teams: trigger from a GitHub issue label or `workflow_dispatch`, have the agent open a PR, humans review.

### Setup

1. Register a GitHub Actions secret with your LLM credential:

```bash
gh secret set ANTHROPIC_API_KEY --repo YOUR_ORG/my-backend
# or:
gh secret set ANTHROPIC_AUTH_TOKEN --repo YOUR_ORG/my-backend
gh variable set ANTHROPIC_BASE_URL --body "https://open.bigmodel.cn/api/anthropic"
```

2. Add a workflow file like `.github/workflows/agent-feature.yml`:

```yaml
name: Agent — feature_delivery

on:
  workflow_dispatch:
    inputs:
      feature:
        description: "One-line feature description"
        required: true
      criteria:
        description: "JSON array of acceptance criteria"
        required: true

jobs:
  run:
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with:
          path: my-backend

      - uses: actions/checkout@v4
        with:
          repository: YOUR_ORG/shadow-gentcore
          path: shadow-gentcore

      - uses: actions/checkout@v4
        with:
          repository: YOUR_ORG/agent-contracts
          path: agent-contracts

      - uses: actions/checkout@v4
        with:
          repository: YOUR_ORG/agent-tools
          path: agent-tools

      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: Install framework
        working-directory: shadow-gentcore
        run: |
          python -m venv .venv
          .venv/bin/pip install -e ../agent-contracts -e ../agent-tools -e .

      - name: Run workflow
        working-directory: shadow-gentcore
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          .venv/bin/ai run workflow ../my-backend/workflows/feature_delivery.yaml \
            --task '{
              "feature": "${{ inputs.feature }}",
              "acceptance_criteria": ${{ inputs.criteria }}
            }'

      - name: Open PR with changes
        working-directory: my-backend
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          git config user.name  "gentcore-agent"
          git config user.email "agent@your-org.invalid"
          BRANCH="agent/feature-$(date +%s)"
          git checkout -b "$BRANCH"
          git add -A
          git commit -m "agent: ${{ inputs.feature }}"
          git push -u origin "$BRANCH"
          gh pr create --title "agent: ${{ inputs.feature }}" \
                      --body "Generated by feature_delivery workflow. Review gates: plan, implement, test, review all passed."
```

### Trigger from the UI

`Actions → Agent — feature_delivery → Run workflow` with your feature + criteria.

### Trigger from an issue

Add a label listener:

```yaml
on:
  issues:
    types: [labeled]

jobs:
  run:
    if: github.event.label.name == 'agent:feature'
    steps:
      # ... same as above, but derive feature from issue title/body
```

## Level 3 — fully automated (narrow scope only)

Only do this when all four are true:

1. The task is **reversible** (doc changes, typo fixes, dependency pins).
2. The workflow has **semantic gates** — `all_passed == true` must actually be provable.
3. The domain has **reset_points** you'd be comfortable rolling back to.
4. You have **drift detection** — a nightly job that compares agent output to canonical patterns.

### Example: nightly dependency update

```yaml
name: Agent — nightly deps refresh

on:
  schedule:
    - cron: "0 9 * * MON"

jobs:
  run:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # ... install framework ...
      - name: Run deps workflow
        run: |
          .venv/bin/ai run workflow ../my-backend/workflows/deps_refresh.yaml \
            --task '{"scope": "minor-and-patch-only"}'
      - name: Auto-merge if all gates green
        run: |
          if grep -q '"status": "completed"' result.json; then
            # PR created → auto-merge if CI is green
            gh pr merge --auto --squash
          else
            echo "gates failed; manual review needed"
            gh pr edit --add-label "needs-review"
          fi
```

For the gate-green path to be safe, the workflow YAML needs:

```yaml
- name: test
  gate: {condition: "all_passed == true", on_fail: abort}  # NOT retry
```

`on_fail: abort` prevents silent retries that might mask real failures in the fully-auto path.

## Watching the self-healing loop

Every workflow run emits an `execution_log` with typed `ExecutionEvent` entries:

```
[step_started             ] plan
[gate_passed              ] plan
[step_started             ] implement
[gate_passed              ] implement
[step_started             ] test
[output_validation_failed ] test         issues: [missing all_passed]
[feedback_loop_triggered  ] test → implement iteration 1
[gate_retry               ] attempt 1, strategy: retry_with_feedback
[gate_passed_on_retry     ] test
[step_started             ] review
[gate_passed              ] review
```

For CI, parse this log to emit structured Slack/PagerDuty alerts:

```python
for entry in result["execution_log"]:
    if entry["event"] in ("FEEDBACK_LOOP_TRIGGERED", "GATE_FAILED", "RETRY_EXHAUSTED"):
        notify_slack(f"{entry['step']} — {entry['event']}: {entry.get('issues', [])}")
```

## Running on a schedule — `cron` pattern

Linux/macOS cron:

```cron
# Every weekday at 7am — refresh generated docs
0 7 * * 1-5 cd ~/shadow-gentcore && ANTHROPIC_API_KEY=sk-... \
  .venv/bin/ai run workflow ~/my-backend/workflows/docs_refresh.yaml \
  --task '{"scope": "api_reference"}' \
  >> ~/logs/agent-docs.log 2>&1
```

Kubernetes CronJob: standard CronJob with the shadow-gentcore container image + your LLM credential in a Secret.

## Webhook pattern — agent-server mode

The `gentcore-template` ships a simple HTTP server (`scripts/agent-server.py`) that accepts `POST /run/agent` and `POST /run/workflow`. See [gentcore-template/README.md](../../gentcore-template/README.md) for the full setup. Key endpoints once it's running:

```bash
# List available agents
curl http://localhost:8765/agents

# Run an agent
curl -X POST http://localhost:8765/run/agent \
  -H "Content-Type: application/json" \
  -d '{"agent": "my-backend/FastAPICodeGenAgent/v1", "task": "Add X"}'

# Run a workflow
curl -X POST http://localhost:8765/run/workflow \
  -H "Content-Type: application/json" \
  -d '{"workflow": "feature_delivery", "task": {"feature": "..."}}'
```

Wire this behind your existing API gateway (Linear webhook, Slack slash command, Jira automation rule, etc.) to trigger runs from anywhere.

## Cost envelopes (real measurements)

Verified on the `acme-backend` feature_delivery workflow:

| Model | Typical cost per run | Files written |
|-------|---------------------|---------------|
| Claude Opus 4.7 | $1.50 – $3.50 | 12 – 18 |
| Claude Sonnet 4.6 | $0.30 – $0.80 | 12 – 18 |
| Claude Haiku 4.5 | $0.05 – $0.15 | 8 – 14 |
| GLM 5.1 (BigModel) | $0.10 – $0.30 | 13 – 15 (production-quality) |
| Gemini 3 Flash | $0.05 – $0.20 | 6 – 10 |
| Minimax M2.7 | $0.08 – $0.20 | 10 – 15 |

**Budgets are enforced** via `workflow.budget.max_cost_usd` and `workflow.budget.max_tokens`. Genesis agents write these into every workflow YAML — check yours after the first build.

## Safety rails we strongly recommend

1. **Always run on a branch.** Never point an agent at `main`.
2. **Enable `trusted: true` deliberately.** Without it, agents prompt before every `file_read`. With it, they're unattended — only enable for repos you fully control.
3. **Run the smoke journey in CI.** `./ai test smoke` is 20 seconds and catches framework drift.
4. **Keep `reset_points`.** Workflows without reset_points can't be rolled back cleanly on partial failure.
5. **Feedback loops have `max_iterations`.** Set it to 2-3, not infinity. The framework won't loop forever — but your budget might.
6. **Monitor `RuleEngine` denials.** A flood of denials means your rules drifted from what agents expect.

## FAQ

**Q: Do I write the workflow YAML myself?**
A: No — genesis writes it. If you want different gates or feedback loops, refine `domain.yaml` and re-run `./ai genesis build --team <name>`. The architect + builder produce everything inside `workflows/` and `agents/` automatically.

**Q: Can I tweak a generated agent prompt?**
A: Technically yes, but your changes get overwritten on the next genesis run. The durable path: refine `context/standards.md` (used by every agent) or add per-capability context docs — genesis picks them up next build.

**Q: What if the stage I need isn't in `_shared/`?**
A: `AgentArchitectAgent/v2` marks that roster entry `decision: synthesize-new` and `_factory/AgentFactoryAgent` synthesises a purpose-built agent for it. You can also pre-seed the catalog by adding to `_shared/` directly before running genesis.

**Q: The same task keeps hitting `retry_exhausted`. What do I do?**
A: The gate is correctly catching a real issue. Options: stronger model (Opus > Sonnet > Haiku), add `reset_points` to earlier in the workflow (regenerate via genesis), or increase `max_iterations` on the feedback loop. See [PROVIDER_GUIDE.md](PROVIDER_GUIDE.md) for model-quality tradeoffs.

**Q: How do I self-improve the genesis agents themselves?**
A: Run `./ai genesis evolve --team <name>` — `EvolutionAgent` reads production run records and refines the existing genesis agents. Opt-in, not default.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| `output_validation_failed: Missing required field` | LLM returned prose instead of JSON | Check [PROVIDER_GUIDE.md](PROVIDER_GUIDE.md) — weaker models need `model_hints.py` nudges or `response_format=json_object` |
| `Gate failed for test` with `all_passed: false` | Correct behaviour — test agent flagged a real issue | Look at `errors[]` in the output; agent will retry with feedback |
| `retry_exhausted` | LLM couldn't converge in N retries | Increase `max_retries`, switch to a stronger model, or add a `reset_points` checkpoint |
| `tool 'file_write' not registered` | `agent-tools` not installed or tool pack path wrong | Run `./ai workspace` — confirms tool packs are loaded |
| Workflow succeeds but no files written | Dry-run mode (`--dry-run` or no API key) | Provide a credential; re-run without `--dry-run` |
| Genesis takes >10 min | Normal for repos with >1000 files | Add `--scan-limit 500` (soon) or narrow `reference:` paths |
